# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Dev Commands

- **Toolchain:** stable Rust (edition 2024), Cargo workspace in `crates/`. pnpm (v9) is only used for the Docker E2E harness.
- `cargo build --workspace` — debug build of `am`, `am-tui`, `am-hook` into `target/debug/`
- `cargo run -p am-cli -- <args>` — run the CLI (`am`). With no args it execs `am-tui` (next to the exe, else `$PATH`), so for the dashboard use `cargo run -p am-tui`
- `cargo test --workspace` — unit, snapshot and integration tests
- `cargo clippy --workspace --all-targets -- -D warnings` — lint (CI fails on any warning)
- `INSTA_UPDATE=always cargo test -p am-tui` — accept changed insta snapshots (`crates/am-tui/src/snapshots/*.snap`); review the diff before committing
- `cargo install --path crates/am-cli && cargo install --path crates/am-tui && cargo install --path crates/am-hook` — install all three binaries to `~/.cargo/bin`, then `am hooks install` to point Claude Code at `am-hook`
- `cargo run -p am-core --example integrations_probe -- <repo> <branch>...` — manual GitHub/Linear fetch against a throwaway DB
- `pnpm test:e2e` — Docker E2E: run the Playwright specs the branch affects (`e2e/affected-specs.sh`) against the real binaries, exit with the tests' exit code; skips the build entirely when nothing affects E2E. Safe to run from several worktrees at once (see Docker E2E Tests)
- `pnpm test:e2e:all` — every spec; `pnpm test:e2e -- 04 09` — just those specs (Playwright file filters)
- `pnpm test:e2e:build` — pre-build the Docker images only
- `pnpm test:e2e:ports` / `bash e2e/run.sh logs` — host ports / container logs of this worktree's running E2E stack
- `pnpm test:e2e:clean` — tear down containers, remove local images and volumes

## What This Is

`agent-monitor` (`am`) is a terminal dashboard for monitoring coding-agent sessions (Claude Code, Codex, Gemini CLI, Cursor, Copilot CLI, Qwen Code, Factory Droid) across git worktrees, written in Rust (ratatui + crossterm, rusqlite). Version 2.x is a native rewrite of the 1.x TypeScript/Ink app and reads and writes the same SQLite DB and `settings.json` in place (history and decisions: `docs/rewrite-plan.md`).

Key capabilities: live agent status from agent CLI hooks through pluggable providers (`am_core::harness`: Claude Code, Gemini CLI, Codex, Qwen Code, Factory Droid, Copilot CLI, Cursor, plus JSON manifests; background Claude subagents → `delegating`), GitHub PR/CI status, Linear tickets and project grouping, stacked-branch detection, worktree create/delete with a live "exists on origin" check, IDE/terminal launching with "resume last agent session", per-repo startup scripts, dev-server detection, and a scriptable CLI with `--json` output.

## Architecture

Three binaries over one library:

| Crate | Binary | Role |
|---|---|---|
| `am-core` | (lib) | Paths, logger, DB + migrations, status rules, settings, grouping/sort, git/worktree ops, integrations, process scan, launching |
| `am-hook` | `am-hook` (lib + bin) | Agent CLI hook handler, on the per-event hot path (~3 ms) |
| `am-tui` | `am-tui` | ratatui dashboard |
| `am-cli` | `am` | clap CLI; no subcommand execs `am-tui` |

### Entry Flow
`am` (`crates/am-cli/src/main.rs`) first checks `argv[1] == "hook-event"` and, if so, calls `am_hook::run_hook_event` **before clap, settings or logger init** (same code as `am-hook`, ~2 ms). Otherwise clap parses the command; usage errors exit 1 (help/version exit 0), matching 1.x scripts. `am mcp` runs the MCP server (`src/mcp/`) and must never print anything to stdout but protocol messages. No subcommand `exec`s `am-tui` via `commands::find_sibling_or_path`; `am setup` passes `--setup` (reopen the wizard) and `am --watch` passes `--log` (open the log pane). Command handlers live in `crates/am-cli/src/commands/`.

`am-tui` (`crates/am-tui/src/main.rs`) loads settings, spawns the collector, shows the first-run setup wizard when `settings.json` lacks `setupCompleted: true`, and runs a single-threaded event loop: drain snapshots and launcher messages → draw only when something changed (or the clock second ticked), inside synchronized-output escapes (DEC 2026) → poll input for 100 ms. Anything slow (git, gh, launching, create/delete) runs on a spawned thread and reports back over an `mpsc` channel (`launcher::Msg`). `e` in Settings opens `settings.json` in the `ide` (an editor or the `ideCommand` custom command, `launcher::open_file`; Settings → Repositories… opens a startup script the same way); with `ide: "terminal"` it runs `$EDITOR` (`edit_file`), which temporarily `ratatui::restore()`s and then re-inits the terminal. The loop checks `settings.json`'s mtime once a second and reloads settings (theme, collector, mouse) when the file's content differs from what the TUI holds, so edits saved in the IDE apply live. Settings → **Run setup again…** (`Action::RunSetup`) closes the editor and opens the wizard with `Setup::new(<registered repo names>, &settings)`; **Reset settings…** asks (`Modal::ConfirmReset`), then `Action::ResetSettings` saves `am_core::settings::reset_to_defaults(current, false)` (known keys to defaults, unknown keys kept, `setupCompleted` dropped) and opens the wizard. Both rows are actions (`Kind::RunSetup`/`Kind::Reset`); their keys are never written. Mouse capture (`EnableMouseCapture`) follows the `mouseEnabled` setting (default on): it is switched off before handing the terminal to `$EDITOR`, on exit and in a wrapped panic hook, and toggled live when the setting changes. Key and mouse events both produce an `Action` that goes through one `dispatch` in `main.rs`.

### UI State
`app.rs` is pure state + key handling (no I/O): a `Snapshot` comes in, `on_key` returns an `Action` that `main.rs` executes. Overlays take keys in priority order: popup (any key closes) → setup wizard → modal (`modals.rs`: new worktree, delete confirm, add repo (the `folder_browser.rs` browser), suggest feature, reset-settings confirm (`y` only), busy for the feature request; modal text wraps and the box grows to fit) → settings editor (`settings_ui.rs`; its repositories, agent-plugins, key-bindings, sort and theme-builder sub-editors take keys first) → help → jobs pane (when focused) → dashboard keys. Dashboard keys go through `App::keymap` (`keymap.rs`): `Keymap::command(key)` → `App::run_command(Command)`. Each `Command` has one rebindable key (default = the 1.x key; overrides in the `keyBindings` setting, only changed keys stored, `none` unbinds) plus fixed keys no command can take (arrows, PgUp/PgDn, Home/End, Tab/Shift-Tab, Esc, Ctrl-C); `o` opens the PR while unbound. `Keymap::from_settings` skips (and WARNs about) unknown ids, unknown/fixed keys and clashes (a changed key beats a default). The key bar, the `?` overlay and `key_available(Command)` read the keymap. Settings → Key bindings… (`keys_ui.rs`, `KeyEditor`): `⏎` captures the next key (a taken key swaps with its holder, a fixed one is refused), `x` resets one, `R` all; every change saves at once and applies live. Overlays (settings, modals, jobs pane, help) keep fixed keys.

**Repositories (`repos_ui.rs`, `folder_browser.rs`):** Settings → Repositories… (`RepoEditor`) lists the tracked repos (most recently used first) with their `~` path (`(missing)` when the directory is gone), worktree count and a `script` tag. `a` opens the add-repo browser, `x` + `y` stops tracking a repo (`worktrees::remove_repository`; worktree rows cascade, nothing on disk is touched), `s`/`⏎` opens its startup script (written from the template first when missing, `Action::EditScript`), and `S` removes the script. `A` on the dashboard (and `n` with no repos) opens the same browser (`FolderBrowser`, port of the 1.x `FolderBrowser`): it starts next to the most recently used repo, lists subdirectories with git repos first (`✓ tracked` ones are refused), and dot-dirs are hidden. `⏎` adds a repo or enters a folder, `→` enters, `←`/Backspace go up, and typing filters by name. A typed `/…` or `~…` path is taken as a path instead (Tab completes). The add runs in `ops::add_repo`; the browser shows `Adding…` and keeps an error open. The setup wizard keeps its typed-path step.

**Jobs pane (background mode, `jobs.rs`):** create and delete run as jobs instead of behind a blocking box. While any job is running, waiting for an answer or failed, a `─Jobs` pane sits to the right of the list (`clamp(width/3, 34, 60)` columns; the log pane and key bar stay full width). Each job shows its stages (create reports them through `worktrees::create_worktree_progress`: checking, fetching, adding, syncing, nickname), any question, and output. Follow-up questions are asked there: **branch exists** (`⏎`/`p` pull, `c` disconnected, `r` reuse, `d` delete + recreate, `n` cancel; the answer re-runs the same job with that `CreateMode`) and **run the startup script?** (`⏎`/`y`, `n`). Focus is never taken automatically: `Tab` moves between the list and the pane (`j`/`k` pick a job, `x` dismisses a finished or failed one), and while a question waits the pane border turns yellow and the key bar shows `⇥ answer`. A successful job lingers 3 s (15 s if it has output), a failure until dismissed; the pane closes when no jobs are left.

`rebuild_rows` turns `snapshot.groups` into visual `Row`s: repo headers (when >1 group, or for the "Other sessions" group), `═ Project ═` headers when the top enabled sort key is `linearProject` (blank line between project sections), `— ENG-123 title —` headers for a ticket shared by 2+ adjacent top-level rows, worktree rows, and `Row::Session(i, k)` rows listing a worktree's live sessions under it when it has 2+ (`├ `/`└ ` connector, own status glyph, harness (plus a short `#3a7c` session id when two sessions share a harness), status · age, `◆ N subagents` from `App::running_subagents_in`, own context bar; the worktree row then shows `⧉ N sessions` in place of its harness, subagent and context badges), `Row::Pending(job)` placeholders for creates (spinner + branch + `creating… <stage>`, or `waiting — ⇥ to answer`) at the end of their repo's group, kept until the snapshot lists the new worktree so nothing flashes. Stacked branches are placed depth-first under their parent with tree prefixes (`├─ `, `└─ `) by `stack_order`; headers only consider top-level rows, so a stack is never split. **Invariant:** headers, session rows and placeholders never take a selection index (a click on a session row selects its worktree; `list_start` keeps the selection's session rows in view); `flat` order always equals the visual order of `Row::Worktree` rows. Selection follows the worktree id across refreshes; `pending_select` selects a just-created worktree once it appears. Deletes run as jobs: `App::deleting` greys the row (spinner + `deleting…`) and blocks row actions on it until the next snapshot after success (a failure frees it immediately). Status changes on unselected rows mark them unseen (`•`) and queue audio cues (`afplay` system sounds) for `waiting`/`done` when `audioNotifications` is on.

**Mouse:** `main.rs` maps crossterm events to `app::Mouse` (`Scroll(±1)`, `Click { x, y, double }`, where a double is a second left-down on the same row within 400 ms). `App::on_mouse(m, terminal_rect)` follows the same overlay priority: popup (click closes) → setup/modal (ignored) → settings editor (wheel = ↑/↓, `SettingsEditor::click` selects a field or changes the selected one) → help (click closes) → dashboard. On the dashboard the wheel acts like ↑/↓ (the job list when the jobs pane has focus), a key-bar hint click runs its action (`ui::BarHit`: a `Command` through `run_command`, or a raw key such as `⇥` through `on_key`; `j/k` isn't clickable), a click in the jobs pane focuses it, a row click selects the row and unfocuses the pane, and a double-click runs `Command::Open` (whatever key it is bound to). Hit-testing (`ui::worktree_at`, `ui::in_jobs_pane`, `ui::keybar_key_at`, `ui::settings_field_at`) uses the same layout helpers as drawing (`dashboard_areas` → `DashAreas`, `list_start`, `keybar_items`, `settings_areas`/`settings_lines`), so the two can't drift apart.

`ui.rs` renders the `─Worktrees` pane (bottom-right `N of M` then ` today 182M ` / ` today (visible) 4.1M ` from `Snapshot.today_tokens` (a `usage::Tally`), shown per `dailyTokensMode` (`tokens` raw, `weighted`, `cost` `~$28.90`, `breakdown` `in · write · read · out`; `tokens_label`: drops `(visible)`, then detail, then itself, when narrow); full width unless the `─Jobs` pane is open beside it; top-right `⬆ vX.Y.Z available` when the update check found a newer release, shortened or dropped on narrow panes, and the settings editor then opens with a banner naming the upgrade command), an optional log pane (`w`, tail of `debug.log`; `L` (`Command::ViewLogs`) opens the log via `launch::log_view(paths::log_files())`: only `debug.log` → the `ide` like `e` in Settings (`launcher::open_file`, or `edit_file` (`$EDITOR` in the TUI) for `terminal`), `debug.log.1` too → `launch::reveal_in_file_manager` (`open -R` / `xdg-open`), none → popup), and a one-line key bar whose hints drop by priority as the width shrinks (per-worktree actions the selection can't take, per `App::key_available`, are dimmed: no PR, no ticket/project, main checkout, a row being deleted), with a transient notice or the `⚠ <source> offline — cached` hint right-aligned. A row is: selection bar `▌`, tree prefix, status glyph, display name (nickname first, then the branch dimmed), badges (`•` unseen, `▶` running processes, bold teal `$ N commands` (`$N` below 100 columns) while an agent's shell command matching `runningProcessFilter` (`procscan::claude_shell_commands_matching`, `WorktreeView.shell_commands`; none without a filter) runs there, which also turns the name bold teal unless the row is waiting, blue `✦ gemini` for a non-Claude agent (`✦` below 100 columns), `◆ N subagents`), then fixed-width columns: Linear ticket, PR (`#42` + `✓`/`✗`/`◌`, `⇡` when merged; coloured by state; then the review state from `review_state`: `approved` (bold green with CI passing, yellow with CI failing/running)/`conflicts`/`changes`/`review`/`draft`, as glyphs below 100 columns), git (`↑ahead ↓behind ±dirty`), last-commit age, and at the far right the context-window bar + tokens used (`ctx_spans`: `█` cells plus a `░▒▓` shade for a part-filled one (no gap before the track), green → yellow at 70% → red at 90%; 8 cells, 5 below 100 columns; hidden when no row has usage; on the `ansi` reversed selection it keeps its colours so the `█` cells stay visible). Columns follow the `show*` settings. `theme.rs` turns an `am_core::themes` spec into ratatui colours (`Theme::load`, falls back to `ansi`). A theme with a `background` paints the whole frame and every overlay (`clear` helper, `Theme::base`). While the theme builder is open, `ui::draw` renders everything with its draft theme, which gives a live preview.

### Data Flow
1. **Agent status in:** the agent CLI runs `"<abs path>/am-hook" hook-event [--agent <id>] --worktree "$CLAUDE_PROJECT_DIR" --event <E>` (written by `am hooks install`; other harnesses' entries add `--agent <id>` and their own project-dir variable, e.g. `$GEMINI_PROJECT_DIR`, or `--worktree ""` (Codex, Copilot), which falls back to the payload's `cwd`) with the JSON payload on stdin. The provider for `--agent` (alias `--harness`; default `claude`) normalises the native payload into the canonical (Claude Code vocabulary) `HookEvent` (`Harness::normalize`; see `docs/agent-providers.md`). `am_hook` walks up to the directory containing `.git` (no git spawn), finds the worktree row (otherwise tracks the path as a standalone session in `standalone_sessions`; a session follows its latest event's owner, and `db::upsert_worktree` promotes a standalone session's rows when its repo is added), does subagent bookkeeping, then applies `am_core::status::map_event_to_status` to **the event's session** (its own previous status and subagent count) in the `sessions` table, and rewrites the owner's `agent_status` (or `standalone_sessions`) row as the headline: the most urgent open session (`status::headline`/`urgency`: waiting > executing > planning > delegating > done > idle), recording its `agent`. Events without a `session_id` update the owner's row directly. A Claude hook whose payload has `cursor_version` is dropped: Cursor runs Claude Code's hooks too, and reports its sessions through its own (`--agent cursor`). Hooks never fail the agent: errors are logged and the process always exits 0, and nothing is printed (Gemini shows hook output to the user). Full rules: `STATUS_MAPPING.md`.
2. **Subagents:** tracked per `(session_id, agent_id)` in the `subagents` table (schema v2), not with a counter. Tool events carrying `agent_id` come *from inside* a subagent: they update only that subagent's row (tool count, last tool + summarized input) and never move the parent status, except a permission prompt → `waiting`. Internal agents (empty `agent_type`) are ignored, duplicate `SubagentStop`s are idempotent, a running row only counts if it was updated in the last 2 h, `SessionStart` closes subagents from other sessions and `SessionEnd` closes the session's own. Descriptions come from Claude Code's `<session>/subagents/agent-<id>.meta.json`. The live count is mirrored into `agent_status.active_subagents` for 1.x compatibility. When the main turn stops with subagents still running the worktree is `delegating`; it becomes `done` when the last one stops.
3. **TUI collector (`am-tui/src/data.rs`):** a `collector` thread holds a long-lived connection and polls `PRAGMA data_version` every 200 ms. The value changes whenever another connection (a hook) commits, so hook writes appear within ~200 ms with no socket. Per cycle: `worktrees::sync_all` every 10 s (picks up worktrees made outside am); a native process scan every 2 s (`procscan`: terminals, VS Code/Cursor windows, dev servers); git status (`gitinfo`, 2 spawns per worktree, run concurrently) only for new rows and worktrees whose `agent_status.updated_at` moved, plus a full sweep every `pollingIntervalMs` (min 5 s) or on `r`; the same stale rows (and standalone sessions whose `updated_at` moved) re-read their context usage from the session transcript (`am_core::context`); stack inference (`stacks`) when branch tips change; and, while `showDailyTokens` is on, every 10 s (and on `r`) today's token usage (`am_core::usage::DailyUsage`, appended transcript bytes only). It marks **parked** subagents (stopped without a `SubagentHandback` while a Claude Code shell command still runs in the worktree, see `procscan::claude_shell_commands`) as running and shows a `done` worktree with one as `delegating` (display only; rules in `STATUS_MAPPING.md`). It then builds views → `grouping::apply_filters` → `grouping::build_groups` → appends "Other sessions" (effectively-open standalone sessions) → `today_tokens` (`dailyTokensScope`: `all` = everything today; `visible` = usage whose cwd's most specific root among *all* worktrees + standalone sessions is a row on screen) and sends a `Snapshot` only if it differs from the last one. The UI coalesces to the newest snapshot.
4. **Integrations thread:** a separate `integrations` thread owns `am_core::integrations::Integrations`. It hydrates from the `integration_cache` table and publishes cached PR/Linear fields before the first fetch, then refreshes GitHub every `ghPollingIntervalMs` and Linear every `linearPollingIntervalMs` (min 30 s each), immediately when the set of branches changes, and on `r` (`force`, subject to `ghRefreshOnManual`/`linearRefreshOnManual`). After a refresh it applies Linear auto-nicknames (`linearAutoNickname`; user-set names are never touched) and sends fields + health to the collector.
5. **Integration cache (offline resilience):** `integrations/cache.rs` uses `integration_cache(kind, cache_key, payload, fetched_at)` with `kind` `pr`/`linear`, `cache_key` `<repo_id>:<branch>`, and camelCase JSON payloads (NULL = fetched OK, none exists). **Only a successful fetch writes**; a failure leaves the old value, so PR badges and ticket/project clustering survive going offline. No TTL: rows are replaced by a later success or pruned when their worktree is gone (an empty worktree list never prunes). `breaker.rs` is a per-source circuit breaker: a network-class failure (DNS, refused, "error connecting", timeouts, 5xx/429) aborts the rest of that source's cycle and backs off 30 s doubling to 15 min; other failures mark the source failing without backoff; WARN only on healthy→failing, INFO on recovery, DEBUG in between; `force` bypasses the backoff. `health()` drives the offline hint. When GitHub has no PR, the Linear ticket's PR attachment for that branch stands in (without checks).
6. **Stacked branches (`stacks.rs`):** a worktree's parent is the worktree whose branch its open PR targets (`baseRefName`). Failing that, git decides: the other worktree branch whose tip is among this branch's commits not yet on the trunk (`origin/<main>` when it exists), choosing the closest one (most unmerged commits). Rev-lists rerun only when a branch tip moves.
7. **Opening (`am-tui/src/launcher.rs` + `am_core::launch`):** `Enter` opens the worktree in the `ide` setting (`launch::IdeChoice`: `vscode` (default), `cursor`, `zed`, `windsurf` via their CLI with an `open -a` fallback, `terminal`, or `custom`, which runs the `ideCommand` setting through `sh -c` with `{path}` replaced by the quoted path, or the path appended; `launch::custom_command`. A custom command still running after 1.5 s counts as opened, an early non-zero exit is an error). With `resumeLastSession` on and no session already visibly open, it resumes the newest session for the worktree root or any subdirectory (`launch::resume_for`): of the agent the hooks last saw (`AgentState.agent`), else the newest of any enabled plugin (`launch::discover_sessions` merges `Harness::discover_sessions`: Claude under `~/.claude/projects/`, confirmed via each transcript's `cwd`; Gemini via `~/.gemini/projects.json` → `~/.gemini/tmp/<slug>/chats/session-*.jsonl`), else a fresh `defaultAgent`. In `terminal` mode the new terminal runs `launch::agent_command` (`claude --resume <id>`, `claude -c` when only hooks know a session, `gemini --resume <id|latest>`). In every editor mode the command is copied to the clipboard (`pbcopy`/`clip`/`xclip`), a popup says so, and the editor opens after ~600 ms. There is no keystroke injection: it needs macOS Accessibility permission and fails silently (osascript error 1002) without it. When a terminal is already open at the worktree, `Enter` (terminal mode) brings the terminal app forward instead. Supported terminals: Terminal.app, iTerm2, Ghostty and Warp (picked from `$TERM_PROGRAM`), and `x-terminal-emulator` on Linux.
8. **Worktree lifecycle (`am_core::worktrees`, called from `am-tui/src/ops.rs` and `am-cli/src/commands/lifecycle.rs`):** worktrees live at `<repo>/.claude/worktrees/<branch with / → ->`. Create = limit check → existence check (`CreateMode::Fresh` only; returns `BranchExists{local,remote}` so the TUI can show the choices) → optional local-branch delete → fetch → `git worktree add` from `origin/<base>` when it exists → sync → nickname. Modes: `Fresh`, `ReuseLocal` (`--reuse`, fast-forwards to origin first), `TrackRemote` (`--track`), `Disconnected` (`--no-track`), `DeleteAndRecreate`. The New Worktree form runs a debounced (400 ms) **advisory** live check (`check_branch`): "✓ exists on origin — Enter will offer to pull it" hides the base field, since the worktree will track `origin/<branch>`; "! exists locally only" offers reuse. Remote existence goes through `remote_branch_probe`, which races `git ls-remote` against a `gh api` ref lookup. The first "yes" wins, and a timeout or failure on one path can't produce a false "no". Delete handles a worktree, a main checkout on a non-default branch (branch only), or a stale row whose directory is gone; the TUI deletes with `force` after showing dirty/unpushed warnings. `check_worktree_limit` (`worktreeLimitEnabled` + `maxWorktrees`, per repo, excluding the main checkout) hard-blocks creation in both the TUI and the CLI. After creating, the TUI's jobs pane offers to run the repo's startup script (`scripts/<repo-id>.sh`): `ops::run_script` runs it in-process with stdin closed and stdout/stderr streamed into the job (ANSI stripped). With `startupScriptMode: "window"` (default `"pane"`) it opens in a new terminal window (`launch::open_terminal`) instead, falling back to the pane when none can be opened.

### Key Modules
`am-core` (`crates/am-core/src/`):
- `harness/` — harness plugins: the CLI or IDE that runs the model, fires the hooks, stores sessions and resumes them; the model is a session attribute (the plugin boundary; design, manifest format and Gemini research in `docs/agent-providers.md`). **Nothing outside this module should name a specific harness** (remaining exceptions are listed in `docs/agent-providers.md`). `mod.rs`: the `Harness` trait (id/name/program/origin/notes, hook settings path + `hooks_key` + `hook_file_defaults` + events + entry shape, `normalize` native payload → canonical `HookEvent`, `discover_sessions`, `resume_args`, `context_usage`, `usage_files`/`usage_record` (today's token total; Claude only so far), `matches_process`, `is_present` = config dir exists, `mcp_config`/`mcp_add_command`/`mcp_remove_command` for `am mcp install`), `HarnessKind` (copyable handle on a registered provider, compared by id; stored in the `agent` column, NULL/unknown = Claude), the open registry (`BUILTIN` + manifest plugins from `<app dir>/agents/*.json`, loaded once per process and `reload()`ed by the TUI collector when `plugins_stamp()` changes; `get` checks built-ins first so built-in hooks never read the dir), `all()`, `plugin_errors()`, `is_enabled`/`enabled`/`detected(&Settings)` (`disabledAgents`), `ProcessSpec`. `manifest.rs`: the declarative format (`events`/`tools`/`fields`/`notificationTypes` maps, `fields` values starting with `/` read as JSON pointers; `hooks` with `layout` `nested` (Claude's) or `flat` (`{command, timeout}` per entry), `commandKey`/`timeoutKey`/`timeoutUnit` (`ms`|`s`), `entry` extra keys, `file` top-level defaults such as `{"version": 1}`, `hooksKey` (`""` = events at the top level), optional `projectDirVar`; ### Persistence
All data lives in `~/.agent-monitor/` (or `$AM_DATA_DIR`): `agent-monitor.db` (SQLite, WAL), `settings.json`, `debug.log` (+ `debug.log.1` after rotation), `scripts/<repo-id>.sh`, `themes/<name>.json` (custom themes), `agents/<id>.json` (harness plugin manifests), `update-check.json` (last release check), and `hook-captures/` (only with `AM_HOOK_CAPTURE=1`). Hook config lives in `~/.claude/settings.json`. The 1.x files `am.sock` and `sessions/` are no longer used.

The DB and `settings.json` are shared with 1.x in place, so never rename or drop a column or setting key. Add schema changes as a new `user_version` step in `db::migrate` (idempotent, in one transaction) and bump `SCHEMA_VERSION`. New settings take their default from `Settings::default()` when absent, and unknown keys must keep round-tripping.

### Data Isolation (`AM_DATA_DIR`)
`am_core::paths::app_dir()` honours `AM_DATA_DIR` and every other path derives from it, so any binary can run against a temp directory without touching real data. Tests set it, plus a temp `HOME` so `~/.claude` is isolated too. Other env vars: `AM_HOOK_BIN`, `AM_NO_NATIVE_HOOK`, `AM_HOOK_CAPTURE`, `AM_LINEAR_API_URL`, `AM_BINARY_DIR` (npm launcher), `AM_PROCSCAN_ROOTS` (procscan probe test only).

## Testing

### Rust tests
- `cargo test --workspace` runs everything; `cargo clippy --workspace --all-targets -- -D warnings` must be clean.
- Unit tests sit next to the code (`#[cfg(test)] mod tests`). Pure logic is tested directly: status rules, grouping/sort, settings parsing, cache/breaker rules, GitHub/Linear response parsing through the `GhRunner`/`HttpTransport` fixtures, procscan with fixture processes, and `worktrees` against real temp git repos.
- `am-tui`: `App` is driven directly with `Key`s; `ui.rs` renders to a ratatui `TestBackend` and compares against **insta** snapshots in `crates/am-tui/src/snapshots/`. After an intended UI change run `INSTA_UPDATE=always cargo test -p am-tui` and review the `.snap` diffs.
- Integration tests: `crates/am-hook/tests/hook.rs` replays real event sequences through the binary; `crates/am-cli/tests/cli.rs` runs `am` with temp `AM_DATA_DIR`/`HOME` and fake `gh`/editor/Linear on `PATH`.
- `log::log` is a no-op under `cfg(test)`, so tests never write the real `debug.log`. Tests that touch process-global env (`AM_DATA_DIR`) hold a lock.

### Docker E2E Tests
End-to-end tests run the real binaries behind ttyd in Docker with GitHub and Linear mocked, driven by Playwright. Use them to capture screenshots and test full flows.

**Parallel runs:** the `pnpm test:e2e*` scripts go through `e2e/run.sh`, which runs compose as project `am-e2e-<checkout dir name>` (override with `AM_E2E_PROJECT`). Containers, network, volumes and built images are prefixed with it, so worktrees never share a stack or overwrite each other's images. Host ports aren't fixed (Docker picks them; `pnpm test:e2e:ports` prints them), because the `tests` container reaches the others over the compose network. Always go through the scripts: a bare `docker compose -f e2e/docker-compose.yml …` uses the shared default project `e2e`.

**Containers** (`e2e/docker-compose.yml`, `e2e/Dockerfile`):
1. **`mock-api`** — `e2e/mock-api/server.ts` on port 4100, serving fixtures from `e2e/mock-api/fixtures/`.
2. **`app`** — a `rust-build` stage (`cargo build --release --locked -p am-tui -p am-cli -p am-hook`, BuildKit cache mounts, LTO off for speed) → `debian:bookworm-slim` with git, ttyd and the fake `gh` (`e2e/bin/gh`, which proxies to mock-api). `e2e/entrypoint.sh` seeds `/work` with a local bare `origin` (`main` plus an origin-only `feature/on-origin`) and a linked worktree `feature/to-delete`, runs `am repo add /work`, writes a startup script for it (so every create asks; `RustTui.createWorktree` declines), and writes settings (`setupCompleted`, `hideMainBranch: false`, Linear on with a mock key, `linearAutoNickname: false`, `runningProcessFilter: "sleep infinity"`) and a fresh `update-check.json` naming `9.9.9` (so the `⬆ v9.9.9 available` notice shows without network). **Affected specs only:** `e2e/affected-specs.sh` maps the branch's changed files (since the merge base with `origin/main`, plus uncommitted and untracked ones; `AM_E2E_BASE` overrides the base) to spec numbers through a `case` table. **Podman memory:** the Podman VM defaults to 2 GB, and one stack (mock-api, app, Chromium) needs roughly 400 MB plus Chromium's peaks. Several worktrees running E2E at once can get Playwright OOM-killed (`Command was killed with SIGKILL`). Give the VM more memory (`podman machine stop && podman machine set --memory 8192 && podman machine start`) or run fewer stacks at once.

## Distribution & Release

- **npm** (GitHub Packages, `@roylet-gs` scope): `@roylet-gs/agent-monitor` is a small Node launcher (`npm/agent-monitor/bin/am.js`) that `spawnSync`s the native `am` from the matching optional dependency `@roylet-gs/agent-monitor-{darwin,linux}-{arm64,x64}` (template `npm/platform/package.json`; each holds `bin/am`, `bin/am-tui`, `bin/am-hook`, and `os`/`cpu` make npm install only the matching one). `AM_BINARY_DIR` overrides the lookup (CI's launcher smoke test uses it). Hooks call `am-hook` by absolute path, so Node is never on the per-event path. See `npm/README.md`.
- **Homebrew:** the repo is its own tap. `npm/agent-monitor.rb.tmpl` is rendered into `Formula/agent-monitor.rb` on each release: `brew tap roylet-gs/agent-monitor https://github.com/roylet-gs/agent-monitor && brew install agent-monitor`.
- **CI** (`.github/workflows/ci.yml`; runs on PRs to main and is reused by publish): clippy `-D warnings` + `cargo test --workspace` on ubuntu and macOS, then builds the binaries and runs `node npm/agent-monitor/bin/am.js --version` against them.
- **Publish** (`.github/workflows/publish.yml`; every push to main except its own `chore: release v…` commit): CI → compute the version → build release binaries for `aarch64`/`x86_64-apple-darwin` and `x86_64`/`aarch64-unknown-linux-gnu` → GitHub Release `vX.Y.Z` with `agent-monitor-vX.Y.Z-<platform>.tar.gz` + `SHA256SUMS` → publish the four platform packages, then the main package with pinned `optionalDependencies` → regenerate the formula, stamp `Cargo.toml`/`Cargo.lock`, commit `chore: release vX.Y.Z` and push.
- **Versioning rule:** the release version is the `[workspace.package] version` in `Cargo.toml` if it is greater than the published npm version, otherwise the next patch past what's published. Bump `Cargo.toml` yourself only for a minor or major release; patch releases happen automatically on merge. All crates use `version.workspace = true`, and each binary's `--version` prints it.
- The release profile uses LTO, one codegen unit, `strip` and `panic = "abort"`.

## Evidence Capture & PR Workflow

### Slash Commands
- `/capture-evidence` — Runs clippy, then spawns two parallel sub-agents: Agent A runs `cargo test --workspace`, Agent B runs `pnpm test:e2e` (affected specs only) for Docker E2E tests and screenshots, using `e2e/affected-specs.sh --explain` to see which specs cover the diff and add specs for gaps.
- `/create-pr` — Idempotent PR creation: clippy + tests, detects an existing PR via `gh pr view`, runs `/capture-evidence`, then creates or updates the PR with the evidence.
- `/merge-main` — Merge the latest main into the branch, then clippy + tests, fix, push.
- `/suggest-changes` — Analyse `am logs` output against the `crates/` sources and propose concrete fixes.

### Scripts (`.claude/scripts/`)
- `upload-evidence.sh [evidence-dir]` — Uploads screenshots as assets to the `evidence-store` GitHub release via `gh release upload --clobber` (branch-prefixed names) and prints the asset URLs. Called with `tests/e2e/tmp`.
- `seed-evidence-data.sh` — **Deprecated.** Local manual debugging only (isolated `AM_DATA_DIR` + `am repo add .`). Use `pnpm test:e2e` instead.
- `capture-tui.sh` — **Deprecated.** Local manual debugging only (serves a command such as `am-tui` via ttyd). Use `pnpm test:e2e` instead.
- `cleanup-tui.sh` — **Deprecated.** Local manual debugging only. Use `pnpm test:e2e:clean` instead.

## Logging

When adding or modifying code paths, add log calls with the `am_core` macros (`use am_core::{debug, info, warn};`; the first argument is the module tag):
- `info!("module", ...)` for key state changes (status updates, hook install/uninstall, worktree create/delete, settings changes, integration recovery)
- `debug!("module", ...)` for branching decisions, mapping logic and timings (e.g. why `map_event_to_status` returned no change). `debug!` checks the level before formatting, so it is cheap when disabled.
- `warn!("module", ...)` for recoverable errors or unexpected state. Don't WARN on every cycle of a repeating failure; log the transition (see `breaker.rs`).
- Always include context (event names, tool names, paths, computed values, elapsed times).

Every call becomes exactly one line (`[ISO] [LEVEL] [module] message`; embedded newlines are joined with ` ⏎ `), written with a single `O_APPEND` write so concurrent hook processes never interleave. Each binary calls `log::init(level, maxLogSizeMb)` at startup, which rotates by renaming `debug.log` → `debug.log.1` once it exceeds `maxLogSizeMb`. Never print to stdout/stderr from `am-tui` (it owns the terminal) or from the hook path.

## Conventions

- Rust edition 2024, resolver 3; shared dependency versions in `[workspace.dependencies]`; every crate inherits the workspace version.
- `cargo clippy --workspace --all-targets -- -D warnings` must pass, and `cargo test --workspace` must stay green on Linux and macOS.
- **No async runtime.** Concurrency is `std::thread` + `std::sync::mpsc` channels (collector, integrations, launcher/ops jobs, scoped threads for parallel git). Blocking work never runs on the UI thread.
- The hook path must stay fast and infallible: no clap/TUI code in `am-hook`, one SQLite connection, no git spawns, always exit 0.
- One SQLite DB is shared by every process (hooks write while the TUI reads): WAL, busy timeout, `PRAGMA user_version` migrations. Keep the schema readable by 1.x (additive changes only).
- External tools are shelled out to (`git`, `gh`, `osascript`/`open`, `pbcopy`) rather than reimplemented, so the user's auth and config apply. Wrap them in traits where tests need fixtures.
- Shared types live in `am_core::model`. Dashboard logic used by both the TUI and the CLI lives in `am_core` (`grouping`, `worktrees`, `integrations`) so they can't diverge.
- `am-tui` keeps state and key handling pure (`app.rs`, `modals.rs`, `settings_ui.rs`, `setup.rs`) and side effects in `main.rs`/`launcher.rs`/`ops.rs`/`data.rs`.
- Unix only (macOS + Linux); `std::os::unix` APIs are fine.
- Published to GitHub Packages as `@roylet-gs/agent-monitor` (plus the per-platform packages) and to the in-repo Homebrew tap.
