# am usage reports: relay and Grafana

How am's anonymous, opt-in usage reports get from users' machines to Grafana Cloud. What users see and what is sent is in [`../TELEMETRY.md`](../TELEMETRY.md); the client side is `crates/am-core/src/telemetry/`.

```
am / am-hook / am-tui ──spool.jsonl──▶ am-tui (every 15 min) ──OTLP/JSON──▶ relay (Cloudflare Worker) ──OTLP + Basic auth──▶ Grafana Cloud (Loki) ──▶ dashboards
```

- **Client:** every binary appends allowlisted events to `~/.agent-monitor/telemetry/spool.jsonl`. `am-tui` posts them to `<endpoint>/v1/logs`, and so does `am telemetry flush`. The endpoint is `upload::DEFAULT_ENDPOINT`, or `AM_TELEMETRY_ENDPOINT`.
- **Relay** (`relay/`): answers 503 (the client keeps the batch and retries) when Grafana is down, throttling, or refuses the relay's own credentials (401/403: a relay misconfiguration, not bad data), and 200 with `partialSuccess` for records it drops. It rebuilds every record from the same allowlist and drops the rest. It never forwards the sender's IP, clamps record times near arrival (Loki refuses entries far older than the newest one in a stream), rate-limits per IP, adds Grafana's credentials and forwards the result. Grafana's token is stored only in the Worker and never ships in the binary.
- **Grafana** (`grafana/`): two dashboards over Loki. Both are generated by `generate.py`.

## One-time setup

### 1. Grafana Cloud

1. Create a stack (the free tier is plenty to start; check the current limits).
2. Find the OTLP endpoint: **your stack → Connections → OpenTelemetry (OTLP) → Configure**. Note the **endpoint** (`https://otlp-gateway-prod-<region>.grafana.net/otlp`) and the **instance ID**.
3. Create a token: **Administration → Users and access → Cloud access policies → Create access policy**. Give it scope `logs:write` only, on this stack, and add a token. A leaked token can only write logs.

### 2. The relay

Requires a Cloudflare account. The Workers free plan covers this.

```bash
cd telemetry/relay
npm test                                            # node --test, no dependencies
# set GRAFANA_OTLP_ENDPOINT in wrangler.toml to your stack's endpoint, then:
npx wrangler@4 login
npx wrangler@4 secret put GRAFANA_INSTANCE_ID       # the instance ID
npx wrangler@4 secret put GRAFANA_API_TOKEN         # the logs:write token
npx wrangler@4 deploy                               # prints https://am-telemetry-relay.<you>.workers.dev
```

For a nicer URL, add a custom domain to the Worker (Workers → am-telemetry-relay → Settings → Domains).

Smoke test with a real install, sending to the relay:

```bash
AM_TELEMETRY_ENDPOINT=https://am-telemetry-relay.<you>.workers.dev am telemetry on
AM_TELEMETRY_ENDPOINT=https://am-telemetry-relay.<you>.workers.dev am repo list
AM_TELEMETRY_ENDPOINT=https://am-telemetry-relay.<you>.workers.dev am telemetry flush   # "Sent 1 event(s)."
```

Then in Grafana → Explore → Loki: `{service_name="am"} | event_name="am.command"`.

### 3. Point releases at it

`DEFAULT_ENDPOINT` in `crates/am-core/src/telemetry/upload.rs` is the relay's URL, **`https://am-telemetry.royle.au`** (the Worker's custom domain in `relay/wrangler.toml`, on the `royle.au` Cloudflare zone; Cloudflare manages its DNS record). A release without an endpoint records reports for users who turned them on (capped at 1 MB, deleted after 7 days) but never sends them.

The live setup: Grafana Cloud stack `merryartichoke3421` (`au-southeast-1`, instance `1897874`), access policy **am telemetry relay** (this stack only, `logs:write`), its token stored only as the Worker secret `GRAFANA_API_TOKEN`. To rotate it: add a token on the policy, check it, then `printf '%s' "$TOKEN" | npx wrangler@4 secret put GRAFANA_API_TOKEN` (a value typed at wrangler's prompt can pick up stray characters), and delete the old token.

### 4. Dashboards

**Dashboards → New → Import**, upload `grafana/am-usage.json` and `grafana/am-health.json`, and pick your stack's Loki data source for **Logs**.

- **am — Adoption & usage:**
  - active installs (24 h / 7 d / 30 d, rolling);
  - versions, OS/CPU, install method;
  - mode, editor, terminal;
  - integrations and options;
  - agent sessions per harness, repos and worktrees per install;
  - dashboard and CLI commands (yours vs. agents' through MCP).
- **am — Errors & performance:**
  - installs hitting an error, crashes;
  - errors by version;
  - where errors happen (file:line, kind, events, installs affected);
  - crashes by location and version;
  - stage p95 across installs, and the share of reports over `perf::BUDGETS`.

### 5. Alerts

In Grafana Alerting, create rules from these queries (Loki data source, evaluated every 5 minutes):

| Alert | Query | Condition |
|---|---|---|
| Crashes | `sum(count_over_time({service_name="am"} \| event_name="am.crash" [1h]))` | > 0 |
| Error spike after a release | `sum by (service_version) (count_over_time({service_name="am"} \| event_name="am.error" \| detected_level="error" [1h]))` | > 10 (tune) |
| New error location | `count(count by (code_filepath, code_lineno) (count_over_time({service_name="am"} \| event_name="am.error" [1h])))` | above last week's |

## Changing the schema

An event or attribute is added in `schema.rs`. Then:

1. Update `TELEMETRY.md`, which is the promise to users.
2. Run `AM_UPDATE_FIXTURES=1 cargo test -p am-core relay_fixture`, which rewrites `relay/test/fixtures/client-body.json`.
3. Update the relay's allowlist (`EVENTS`, `RESOURCE_KEYS`) if needed, and run `npm test`. The fixture test fails until both sides agree.
4. Redeploy the relay before releasing the client. A relay that doesn't know an event drops it.

## Working on the dashboards locally

Edit `grafana/generate.py`, not the JSON. To check every panel against real Loki:

```bash
podman run -d --name am-lgtm -p 13000:3000 -p 14318:4318 docker.io/grafana/otel-lgtm   # or docker
node telemetry/grafana/seed-local.mjs "$PWD/telemetry/relay/src/worker.js" telemetry/relay/test/fixtures/client-body.json
python3 telemetry/grafana/generate.py telemetry/grafana
python3 telemetry/grafana/check.py telemetry/grafana/*.json     # every query: errors and empty results
# import them at http://localhost:13000 (admin/admin) to look at them
podman rm -f am-lgtm
```

`seed-local.mjs` sends 12 synthetic installs' worth of every event through the real relay code. Panels for harnesses the seed doesn't include (cursor, copilot, …) stay empty.

What we learned from doing this against otel-lgtm:

- Only `service_name` is an index label. Every other attribute, from resource or record (`event_name`, `am_install_id`, `service_version`, `command`, `code_filepath`, …), is structured metadata with dots turned into underscores. Filter it after the selector.
- Instant queries ignore `legendFormat`. Panels with several instant queries name them with `byFrameRefID` overrides (`named()` in the generator). Breakdowns use range queries over `[$__interval]`, summed by the panel (`summed()`).
- A ratio whose numerator can be empty needs `(…) or vector(0)`, or the panel says "No data" instead of 0%.
